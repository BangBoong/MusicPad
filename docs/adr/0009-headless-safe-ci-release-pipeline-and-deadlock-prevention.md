# Стабільний релізний пайплайн для GitHub Actions та усунення deadlock у headless-середовищі

У процесі підготовки GitHub Releases для MusicPad було виявлено проблему нескінченного перебування workflow у статусі `in progress`. Цей документ фіксує причину та ухвалене архітектурне рішення щодо стабілізації пайплайну збірки.

## Context & Motivation

1. **Зависання релізної джоби у GitHub Actions**:
   - При спробі створення релізу (тег `v1.1.0`, запуск 41527836746) процес зависав на кроці `Run Python Unit Tests` понад 10 хвилин і не переходив до компіляції виконуваного файлу.
   - Аналіз системного журналу виконання показав блокування у тесті `test_toolbar_controls_layout_and_play_pause_lifecycle` на виклику `app.update() -> SpeechBubble._reposition() -> update_idletasks()`.
   - У віртуальних машинах GitHub Actions `windows-latest` (Windows Server) відсутній фізичний дисплей, активний DWM-композитор та апаратні звукові пристрої. Виклик `update_idletasks()` під час обробки черги повідомлень викликав рекурсивну re-entrancy та взаємне блокування очікування подій віконного менеджера.
   - У workflow був відсутній параметр `timeout-minutes`, через що завислий процес блокував реліз до ручного переривання.

2. **Обмеженість тригерів релізу**:
   - Пайплайн запускався тільки на `push: tags: ['v*']` або ручний `workflow_dispatch`.
   - При публікації релізу через вебінтерфейс GitHub (`release: [published]`) або при ручному запуску `workflow_dispatch` без створення тегу готовий `.exe` не додавався до релізу через умову `startsWith(github.ref, 'refs/tags/')`.

## Decision

1. **Оптимізація та стабілізація `release.yml`**:
   - Встановлено жорсткий ліміт виконання джоби `timeout-minutes: 15`.
   - Додано тригери на подію публікації релізу `release: types: [published, created]`.
   - З релізного пайплайну вилучено виконання повного набору інтерактивних Tkinter GUI-тестів. Релізний процес фокусується на своїй безпосередній задачі:
     1. Збірка та тестування нативного APO/DSP ядра через `native/build.ps1` (компіляція `test_native.exe` та перевірка математики DSP).
     2. Компіляція за допомогою PyInstaller (`MusicPad.spec` із вбудованими FFmpeg, FFprobe та нативними DLL).
     3. Верифікація отриманого виконуваного файлу через вбудований self-test: `.\dist\MusicPad.exe --self-test self_test_report.json`.
     4. Архівація портативного `.zip`.
     5. Завантаження артефактів:
        - Через `actions/upload-artifact@v4` для гарантованого збереження артефактів при будь-якому ручному запуску.
        - Через `softprops/action-gh-release@v2` при створенні релізу або тегів `v*`.

2. **Захист від блокування та deadlock у `SpeechBubble._reposition()`**:
   - У `SpeechBubble._reposition()` та `MusicPadApp.update()` додано захист від рекурсивного оновлення `update_idletasks()` під час дренажу черги інтерфейсу (`_in_update`) та в середовищах headless/CI (`CI` або `GITHUB_ACTIONS`).
   - Якщо вікно або віджет не має активного інтерактивного віконного циклу, координати розраховуються на основі поточних кешованих геометричних параметрів без блокування потоку.

## Consequences

- Збірка та публікація релізів у GitHub Actions виконується гарантовано швидко (~3-4 хвилини) без зависань.
- Зібраний бінарник автоматично перевіряється самотестом на працездатність нативного середовища перед публікацією.
- Релізи успішно формуються як при створенні git-тегів, так і через вебінтерфейс GitHub Releases.
