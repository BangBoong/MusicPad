# Startup Performance: onedir-збірка, вимкнення UPX та відкладена ініціалізація

Див. [ADR-0020](../../docs/adr/0020-stay-on-python-native-hot-path.md) — рішення залишатися на Python замість переписування на Rust.

## Problem Statement

Користувач запускає `MusicPad.exe` і довго чекає на появу вікна. Причина не в мові програми:
1. Релізний `MusicPad.exe` — PyInstaller **onefile** розміром ~259 МБ зі стисненням **UPX**. При кожному запуску весь вміст (рантайм Python, numpy, FFmpeg/FFprobe, нативні DLL, модель DeepFilterNet) розпаковується в тимчасову теку, попередньо розтискаючись з UPX, а антивірус сканує щойно розпаковані DLL.
2. Важкі модулі (`yt_dlp`, `ytmusicapi`, `numpy`, `sounddevice`, `PIL`, `pystray`) імпортуються на рівні модулів ще до створення вікна, хоча пошук YouTube потрібен не одразу.
3. Ініціалізація аудіо (відкриття пристроїв, перевірка стану драйвера, завантаження моделі шумозаглушення DeepFilterNet) відбувається до показу інтерфейсу — навіть коли шумозаглушення вимкнене.
4. Немає виміряної базової лінії, тому неможливо довести, яка зміна допомогла.

Додатково спостерігаються підвисання інтерфейсу; це менш пріоритетно й виділяється в окрему задачу.

## Solution

- Спершу виміряти базову лінію часу до появи вікна (зібраний бінарник і `python main.py`) та розбивку `python -X importtime`.
- Публікувати в GitHub Releases лише **портативний ZIP onedir-збірки**: користувач розпаковує одну теку `MusicPad/` і запускає `MusicPad.exe` (поруч лежить `_internal/`). Нічого не розпаковується під час запуску. UPX вимкнено.
- Якщо користувач запускає `MusicPad.exe` прямо з ZIP-архіву у провіднику Windows, програма показує зрозуміле повідомлення «Спочатку розпакуйте ZIP» замість падіння.
- Вікно з'являється першим. Після цього у фоні прогріваються модулі пошуку YouTube, а аудіопідсистема ініціалізується протягом ~1 с. Дії користувача, зроблені до готовності (пошук, відтворення, гарячі клавіші), не губляться — вони виконуються автоматично, щойно відповідна частина готова.
- Модель шумозаглушення DeepFilterNet завантажується лише тоді, коли шумозаглушення увімкнене.
- Портативність зберігається: дані в `.cache/` поруч із `MusicPad.exe`; оновлення — розпакування нового ZIP поверх старої теки.
- Ціль: вікно з'являється за **≤ ~2 с при теплому запуску** на машині розробника (уточнюється після базової лінії).

## User Stories

1. As a користувач, I want бачити вікно MusicPad за ~2 секунди після подвійного кліку, so that програма відчувається швидкою і я не думаю, що вона зависла.
2. As a користувач, I want завантажити з GitHub Releases один ZIP, розпакувати його та запустити `MusicPad.exe`, so that встановлення залишається простим і портативним.
3. As a користувач, I want бачити в розпакованій теці лише `MusicPad.exe` і одну теку `_internal/`, so that одразу зрозуміло, що запускати.
4. As a користувач, який двічі клацнув `MusicPad.exe` всередині ZIP у провіднику Windows, I want побачити повідомлення «Спочатку розпакуйте ZIP», so that я розумію, що робити, замість загадкового падіння.
5. As a користувач, I want оновлювати MusicPad, розпакувавши новий ZIP поверх старої теки, so that мої налаштування, список звуків, записи та кеш YouTube зберігаються.
6. As a новий користувач, I want щоб програма працювала після першого розпакування без наявної теки `.cache/`, so that мені не треба нічого створювати вручну.
7. As a користувач, I want README з чіткою інструкцією розпаковувати в теку з правом запису (Робочий стіл, Документи, `D:\Apps`), а не в `Program Files`, so that налаштування зберігаються.
8. As a користувач, I want щоб антивірус рідше давав хибні спрацювання на MusicPad, so that мені не доводиться додавати винятки (наслідок відмови від UPX та розпакування в тимчасову теку).
9. As a користувач, який одразу після запуску вводить запит у пошуковий рядок YouTube і натискає `Enter`, I want бачити стан «Завантаження…» і автоматичний пошук після прогріву, so that мій запит не губиться і не з'являється помилка.
10. As a користувач, який вставляє посилання YouTube одразу після запуску, I want щоб пряме відтворення за посиланням спрацювало після прогріву, so that поведінка така сама, як у вже прогрітій програмі.
11. As a користувач, який вводить текст до завершення прогріву, I want щоб пошукові підказки з'явилися, щойно модулі готові, so that автодоповнення працює без помилок.
12. As a користувач, який натискає відтворення треку одразу після появи вікна, I want щоб трек почав грати, щойно аудіо готове (≤ ~1 с), so that клік не губиться.
13. As a користувач, який натискає гарячу клавішу саундпада одразу після запуску, I want щоб дія виконалася після готовності аудіо, so that гарячі клавіші надійні з першої секунди.
14. As a користувач, I want щоб кнопки відтворення не виглядали зламаними під час короткої ініціалізації аудіо, so that інтерфейс не мерехтить станами disabled/enabled.
15. As a користувач із вимкненим шумозаглушенням DeepFilterNet, I want щоб модель не завантажувалася при запуску, so that запуск швидший і споживання пам'яті менше.
16. As a користувач, який вмикає шумозаглушення DeepFilterNet у налаштуваннях, I want щоб модель завантажилася у фоні й шумозаглушення почало працювати без зависання інтерфейсу, so that перемикання плавне.
17. As a користувач з увімкненим шумозаглушенням DeepFilterNet, I want щоб воно запрацювало автоматично після запуску, so that моя обробка голосу не залежить від того, що змінилася послідовність ініціалізації.
18. As a користувач у режимі «Ін'єкція в мікрофон», I want щоб стан драйвера відобразився коректно після відкладеної ініціалізації, so that я бачу, чи працює ін'єкція.
19. As a користувач, який згорнув програму в трей при закритті, I want щоб іконка трею з'являлася як і раніше, so that поведінка трею не регресує через лінивий імпорт `pystray`.
20. As a розробник, I want скрипт, що вимірює медіанний час до появи видимого вікна «MusicPad» за N запусків для довільної команди, so that я можу порівняти onefile, onedir і `python main.py` об'єктивно.
21. As a розробник, I want розбивку `python -X importtime`, збережену поруч зі специфікацією, so that видно, які імпорти найдорожчі.
22. As a розробник, I want щоб самотест зібраного бінарника звітував `onedir`, `window_shown_ms`, `audio_ready_ms` і факт, що важкі модулі не завантажені до появи вікна, so that регресії швидкодії ловляться в CI.
23. As a розробник, I want щоб релізний пайплайн збирав onedir, запускав самотест для `dist/MusicPad/MusicPad.exe`, архівував усю теку і публікував лише ZIP, so that реліз відповідає новому формату.
24. As a розробник, I want щоб локальна onedir-збірка в `dist/MusicPad/` продовжувала використовувати `.cache/` у корені репозиторію, so that розробка й наявні тести не ламаються.
25. As a розробник, I want тестами керувати моментом завершення фонового прогріву, so that тести відкладеної ініціалізації детерміновані, а не залежать від таймінгів.
26. As a розробник, I want текстові перевірки `MusicPad.spec` і `release.yml` на `upx=False`, onedir та відсутність onefile-артефакту, so that ніхто випадково не поверне повільне пакування.
27. As a мейнтейнер, I want оновлені обидва README (EN/UA) та визначення «Релізного пайплайну» в глосарії, so that документація відповідає новому формату релізу.
28. As a мейнтейнер, I want окрему задачу на дослідження підвисань інтерфейсу, so that вона не загубилася, але не блокує роботу над запуском.

## Implementation Decisions

- **Базова лінія спершу.** Додати dev-скрипт вимірювання запуску: запускає задану команду, опитує появу видимого верхньорівневого вікна з заголовком «MusicPad» (через Win32 `FindWindowW` / `IsWindowVisible` по `ctypes`), завершує процес, повторює N разів і виводить медіану/мін/макс. Вимірювання ззовні обов'язкове: в onefile-режимі розпакування виконує окремий процес-завантажувач, якого самотест не бачить. Результати базової лінії (onefile, `python main.py`, `-X importtime` top-N) записати в коментар задачі 01. Скрипт не входить у CI.
- **Пакування.** `MusicPad.spec` переходить на onedir: `EXE` із `exclude_binaries=True` + `COLLECT` з іменем `MusicPad`; `upx=False` для `EXE` і `COLLECT`. Перелік вбудованих ресурсів (FFmpeg/FFprobe, нативні DLL, модель DeepFilterNet, дані `ytmusicapi`, assets) не змінюється. Наявні пошуки ресурсів через `_MEIPASS` працюють без змін (в onedir `_MEIPASS` = `_internal/`).
- **Релізний пайплайн.** Самотест запускається для `dist/MusicPad/MusicPad.exe`; ZIP `MusicPad-windows-x64.zip` містить теку `MusicPad/` (+ README, іконку); onefile `MusicPad.exe` більше не завантажується ні в Actions artifacts, ні в GitHub Release. Решта ADR-0009 (таймаут, тригери) без змін.
- **Корінь застосунку в dev-збірці.** Правило визначення кореня застосунку (дублюється в головному модулі та аудіорушії) розширюється: якщо тека exe лежить у теці `dist`, а поруч із `dist` є `MusicPad.spec` — коренем вважається корінь репозиторію. Наявне правило «exe безпосередньо в `dist`» зберігається. Для релізних користувачів коренем лишається тека з `MusicPad.exe`. Логіку бажано звести в одну спільну функцію.
- **Захист від запуску з ZIP.** На самому початку точки входу у frozen-режимі, до імпорту важких модулів і до Tk: якщо поруч з exe немає `_internal/` або шлях exe знаходиться в тимчасовій теці, куди провідник Windows копіює файли з ZIP, — показати нативний `MessageBoxW` «Спочатку розпакуйте ZIP» (UK/EN за мовою системи) і завершитися з ненульовим кодом.
- **Лінивий прогрів модулів пошуку.** `yt_dlp`, `ytmusicapi` і `PIL` не імпортуються на рівні модулів. Аудіорушій отримує явну точку прогріву (запуск у фоновому daemon-потоці після першого показу вікна через `after`) і подію/стан готовності. Усі методи пошуку, пошукових підказок, альбомів, обкладинок і прямого відтворення за посиланням спершу чекають готовності (у фоновому робочому потоці, не в UI-потоці). `pystray` імпортується при першому використанні трею.
- **Стан «Завантаження…» пошуку.** Якщо пошук запущено до готовності прогріву, панель пошуку показує локалізований стан «Завантаження…» / «Loading…», а запит виконується автоматично після готовності. Пошукові підказки до готовності не запитуються; після готовності — запитуються для поточного тексту поля. Помилка прогріву показується як звичайна помилка пошуку.
- **Відкладена ініціалізація аудіо.** Відкриття аудіопристроїв і перевірка стану драйвера виконуються одразу після першого показу вікна. Бюджет — ≤ ~1 с від показу вікна. Дії відтворення (клік, подвійний клік, гарячі клавіші саундпада, відновлення стану) до готовності ставляться в чергу; виконується остання дія відтворення (а не всі накопичені), щойно аудіо готове. Кнопки візуально не вимикаються.
- **DeepFilterNet за вимогою.** Модель/бібліотека шумозаглушення DeepFilterNet завантажується лише якщо шумозаглушення увімкнене (при запуску — у фоні після готовності аудіо; при ввімкненні в налаштуваннях — у фоні без блокування UI). Поки модель вантажиться, голос проходить без цієї стадії обробки голосу.
- **Самотест.** Звіт доповнюється полями `onedir` (наявність `_internal/` у frozen-режимі), `window_shown_ms`, `audio_ready_ms` (від старту Python-процесу), `heavy_modules_loaded_before_window` (чи були `yt_dlp`/`ytmusicapi`/`PIL` у `sys.modules` на момент показу вікна). Поля `has_yt_dlp`/`has_ytmusic` звітуються після явного очікування прогріву. `ok` додатково вимагає `heavy_modules_loaded_before_window == false` і `audio_ready_ms - window_shown_ms <= 1000`; у frozen-режимі — `onedir == true`.
- **Документація.** Обидва README: «завантажте ZIP → розпакуйте → запустіть `MusicPad.exe`», «оновлення — розпакуйте поверх старої теки», «розпаковуйте в теку з правом запису, не в `Program Files`». Визначення «Релізного пайплайну» в глосарії оновлюється з «портативний виконуваний файл» на «портативну onedir-теку в ZIP».

## Testing Decisions

- Добрий тест перевіряє зовнішню поведінку (що бачить користувач або що звітує бінарник), а не внутрішню будову: наприклад, «пошук до прогріву показав „Завантаження…“ і повернув результати», а не «викликано метод X».
- **Шов 1 — самотест зібраного бінарника** (найвищий, наявний). `test_compiled_exe_window_and_self_test` оновлюється на `dist/MusicPad/MusicPad.exe` і перевіряє нові поля звіту; CI-крок самотесту — на новий шлях. Очікувані шляхи `.cache` лишаються в корені репозиторію (завдяки правилу кореня в dev-збірці).
- **Шов 2 — in-process тести `MusicPadApp`** (наявний клас GUI-тестів). Прогрів і готовність аудіо мають керовану з тестів точку (наприклад, підміна фонового прогріву на подію, яку тест відпускає вручну), щоб тести були детермінованими. Покривають: пошук до прогріву → «Завантаження…» → результати; підказки після прогріву; відтворення/гаряча клавіша до готовності аудіо → виконання після готовності (лише остання дія); DeepFilterNet не завантажується при вимкненому шумозаглушенні та завантажується при ввімкненні; правило кореня застосунку для `dist/MusicPad/`; захист від запуску з ZIP через підміну `sys.frozen` / `sys.executable` / `_MEIPASS` — за зразком наявних тестів frozen-шляхів та вбудовування FFmpeg/FFprobe.
- **Шов 3 — текстові перевірки** `MusicPad.spec` і `release.yml` (наявна практика в тесті вбудовування FFmpeg/FFprobe): `upx=False`, наявність `COLLECT`, архівація теки `dist/MusicPad`, відсутність завантаження onefile `dist/MusicPad.exe`.
- Скрипт вимірювання запуску — ручний інструмент для базової лінії та прийняття цілі ≤ ~2 с; у CI не запускається (таймінги GitHub-раннерів нестабільні).

## Out of Scope

- Переписування на Rust або іншу мову (див. ADR-0020).
- Перенесення користувацьких даних у `%APPDATA%` та міграція даних.
- Будь-яка обробка встановлення в теки без права запису, крім рядка в README.
- Інсталятор (MSI/Inno Setup), автооновлення, підпис коду.
- Зменшення розміру FFmpeg/FFprobe або інших вбудованих бінарників.
- Виправлення підвисань інтерфейсу (лише заведення окремої задачі 05).
- Зміни драйвера MusicPad, DSP-ядра чи буфера ін'єкції.

## Further Notes

- Задачі та блокування: 01 (базова лінія) і 02 (префакторинг кореня застосунку) — одразу; 03 (onedir ZIP без UPX) ← 01, 02; 04 (захист від запуску з ZIP) ← 03; 05 (фоновий прогрів пошуку) ← 01; 06 (DeepFilterNet за вимогою) ← 01; 07 (відкладене аудіо з чергою відтворення) ← 05, 06. 08 (підвисання інтерфейсу) — окрема, `needs-triage`.
- Якщо після 07 ініціалізація аудіо не вкладається в ~1 с — не послаблювати бюджет мовчки, а дослідити, що саме повільне, і зафіксувати в коментарі задачі 07.
- Можлива прогалина в глосарії: стан «фоновий прогрів» (вікно видиме, пошук/аудіо ще готуються) — кандидат для `/domain-modeling`, якщо термін закріпиться.
